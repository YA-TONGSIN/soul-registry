## ① 변조 알림

**목적.** 로컬 SOUL·MEMORY 파일이 장부의 최신 버전과 같은지 매일 확인하고, 다르면 알린다. 근거: soul-verify v0.8 exp1 — 행동 테스트만으로는 몰래 바뀐 SOUL을 다 잡지 못했고, 파일 지문(SHA-256)이 잡았다. 행동 검사는 보조, 지문 대조가 기본 방어선이다.

**사용자 흐름.**
1. 한 번만: SOUL을 장부에 기록해 둔다(직접 등록 또는 무료 묶음).
2. 작업 스케줄러/OpenClaw 자동화가 하루 한 번 `node scripts/check-soul.js --agent <id> <SOUL 경로>`를 실행한다.
3. 종료 코드 0이면 조용히 끝, 1이면 "최신 버전과 다름(어느 옛 버전과 같은지 / 어떤 기록과도 다름)" 알림, 2면 "확인 못 함(네트워크 등)".
4. 의도한 변경이면 새 버전으로 기록(②가 이 단계를 자동화)하고, 의도하지 않았다면 파일을 되돌린다.

**필요한 변경.**
- 컨트랙트: 없음. 읽기(`getAgent`, `getHistory`)만 쓴다.
- 스크립트: `scripts/check-soul.js`(구현됨), `test/check-soul.test.js`(8개). LF 정규화 해시 + 원본 바이트 해시 둘 다 비교 → v1~v4(CRLF 기준 기록)도 인식.
- 화면: 없음. 이후 조회 페이지에 "내 파일 지문 넣고 일치 확인"이 이미 있어 같은 규칙을 쓴다.

**위험.**
- 줄바꿈·BOM·끝 공백 차이로 "다름" 오탐 → LF 정규화로 줄바꿈만 흡수. BOM/공백은 의도적으로 정규화하지 않는다(정규화 범위를 넓히면 변조를 가릴 수 있다).
- 공개 RPC 장애·속도 제한 → 종료 코드 2로 구분해 "변조"와 섞이지 않게 함. 재시도는 호출 쪽(스케줄러) 책임.
- 근본 한계: 파일과 감시 스크립트가 같은 PC에 있으면 PC를 장악한 공격자는 스크립트도 바꿀 수 있다. 장부(외부)가 기준이라는 점이 장점이지, 로컬 탈취를 막는 장치는 아니다.
- 지문은 "같음/다름"만 알려 준다. **무엇이** 바뀌었는지는 모른다(본문을 올리지 않기 때문). 이 점을 알림 문구에 명시.

**작업량.** 소. 알림 전달(디스코드·메일)은 자동화 쪽에서 종료 코드를 받아 처리.

## ② 자동 기록

> **구현 상태(2026-10-28, 로컬):** 위험 절의 결론대로 **"변경 감지 → 대기 항목(pending/) → 사람이 승인해야 서명"**이 기본이다. `watch-soul.js`(감지만, 지문·시각·직전 버전·diff 줄 수만 기록), `approve-soul.js`(기본 DRY, 소유자 키는 환경변수로만, 거절 시 `rejected/`에 "몰래 바뀜 의심" 표시), `check-soul.js --batches-dir`(앵커된 서명도 최신으로 인정). 묶음 올리기는 기존 `anchorBatch` 흐름을 그대로 쓴다(새 스크립트 없음). 아래 본문의 `sign-entry.js`·`build-batch.js`·"서명 JSON을 창구로 자동 전송"은 구현하지 않았다. 완전 자동 서명은 구현하지 않았고 옵션으로 남는다. README "자동 기록" 절 참고.

**목적.** OpenClaw 등에서 SOUL이 바뀌면 사람이 손대지 않아도 새 버전이 장부에 남게 한다. 지갑·가스 없이, 기존 EIP-712 서명 + Merkle 묶음(`anchorBatch`) 방식을 그대로 쓴다.

**사용자 흐름.**
1. 최초 1회: 사용자가 서명용 키를 하나 만든다(자산 없는 전용 키, 가스 불필요). 에이전트 이름·키를 감시 스크립트에 연결.
2. 감시 스크립트(파일 변경 감지 또는 하루 1회 점검)가 SOUL의 LF-SHA-256을 계산. 마지막으로 기록한 해시와 다르면 `SoulEntry{owner, agentName, soulHash, parentHash, note, signedAt}`에 서명해 **서명 JSON을 묶음 제출 창구**로 보낸다.
3. 운영자가 하루치를 모아 Merkle root를 `anchorBatch`로 올리고, 각 사용자에게 `{entry, signature, proof}`를 돌려준다. 이후 `verifyBatchEntry`로 누구나 검증.
4. 자동 기록은 `note`에 "auto: 파일 지문 변경 감지" 같은 출처 표기를 넣어 사람이 직접 쓴 메모와 구분.

**필요한 변경.**
- 컨트랙트: 없음. (묶음 항목은 체인의 `parentHash` 규칙을 강제하지 않는다 — DESIGN.md의 알려진 한계. 계보는 ③에서 오프체인으로 재구성.)
- 스크립트: `scripts/sign-entry.js`(키로 EIP-712 서명, `lib/merkle.js`의 도메인·타입 재사용), `scripts/watch-soul.js`(해시 변경 감지 → 서명 JSON 생성, 사전 마지막 기록 해시 저장), 운영 쪽 `scripts/build-batch.js`(서명 모아 root·proof 생성, 기존 `demo-batch.js`를 일반화).
- 화면: `register/`에 "서명 JSON 불러오기 → 묶음 증명 확인"은 이미 있음. 변경 불필요.
- 연동: OpenClaw 쪽은 SOUL 변경 훅 또는 자동화로 `watch-soul.js` 호출. 외부 서비스에 보내는 것은 서명 JSON(해시·이름·메모)뿐.

**위험.**
- **서명 키 보관**: 이 키가 새면 남이 내 이름으로 "내 SOUL 변경"을 기록할 수 있다. 전용 키, 파일 권한 제한, 자산 보관 금지, 키 분실 시 새 에이전트로 이전하는 절차를 문서화.
- **자동 기록이 변조를 정상화**: 누군가 SOUL을 몰래 바꾸면 자동 기록이 그 변조본을 새 버전으로 박제한다. → 자동 기록은 ①의 알림과 **분리**한다. 기본값은 "변경 감지 시 알림만, 서명은 사람 확인 후" 또는 "변경 후 N시간 유예 + 알림". 완전 자동은 옵션.
- 운영자 의존: 묶음을 올리는 주체가 멈추면 지연된다(서명은 남아 있어 나중에 올릴 수 있음). `signedAt`과 anchor 시각을 모두 표시.
- 하루 한 번 묶음 앵커링 비용은 기존 추정(약 $0.0016/일 가스) 그대로. 메인넷 전환은 별도 결정.

**작업량.** 중 (키 보관·유예 정책 설계에 시간이 듦, 코드는 크지 않음).

## ③ 계보 나무 화면

**목적.** SOUL 버전 체인과 갈라짐(fork)을 한눈에 보여 준다. 원칙: **덮어쓰지 않고 갈라서 남긴다.** 되돌리거나 다른 길로 가고 싶으면 이전 기록을 고치는 게 아니라, 이전 버전에서 새 가지를 낸다.

**사용자 흐름.**
1. 조회 페이지에서 agentId(또는 이름) 입력 → 세로/가로 나무: 노드 = 버전(해시 앞 8자리, 날짜, 메모), 선 = parent.
2. 같은 부모를 가리키는 노드가 둘 이상이면 가지로 표시, 현재 head에 강조.
3. 내 파일을 끌어다 놓으면(지문만 계산) 해당 노드가 켜짐 — ①과 같은 규칙.
4. "여기서 갈라서 시작" 안내: 새 에이전트를 등록하며 `metaURI`/note에 부모(`agentId#버전 해시`)를 적는 절차를 보여 준다.

**컨트랙트 변경 필요 여부 (검토 결과: 필수 아님).**
- 한 에이전트 안에서는 `appendSoul`이 `parentHash == head`를 강제해 **가지가 생길 수 없다**(의도된 설계). 가지 = 다른 에이전트 ID.
- 에이전트 간 연결은 이미 있는 `registerAgent(..., metaURI)` / `note`에 `fork-of:<agentId>:<soulHash>` 규약을 정하면 된다. 컨트랙트를 건드리지 않는 MVP.
- 묶음(무료) 항목은 `parentHash`를 서명에 담고 있으므로 같은 부모를 가리키는 서명이 둘이어도 오프체인에서 가지로 그릴 수 있다.
- 선택 개선(나중): `forkOf(parentAgentId, parentHash)`를 이벤트로 남기는 `registerFork` 추가 시 가지를 검증 가능한 사실로 만들 수 있다. 단, 배포된 컨트랙트 교체가 필요하고 기존 에이전트가 이전되지 않으므로 **실사용 수요가 확인된 뒤** 결정. 지금은 권하지 않는다.

**필요한 변경.**
- 컨트랙트: 없음(MVP).
- 스크립트: `scripts/export-lineage.js`(이벤트 `SoulAppended`·`AgentRegistered` 읽어 `lineage.json` 생성; 읽기 전용).
- 화면: `register/`에 "계보" 탭(정적 SVG, 외부 요청 없음; 기존 CSP 유지). 순수 JS로 노드 배치(버전 수십 개 규모면 충분).

**위험.**
- `fork-of` 표기는 **주장일 뿐** 검증되지 않는다(누구나 남의 해시를 부모라 적을 수 있음). 화면에 "자기 신고"라고 표기, 부모 에이전트의 소유자 서명이 있을 때만 "확인됨" 표시하는 단계는 후속.
- 같은 SOUL을 두 에이전트가 올리면 선후는 타임스탬프로만 구분(먼저 올린 쪽이 원본이라는 증거는 약함).
- 이벤트 조회는 공개 RPC의 `getLogs` 제한(범위·속도)에 걸릴 수 있음 → 배포 블록부터 청크 조회 + 결과 캐시.

**작업량.** 중 (화면 작업이 대부분).

## ④ SOUL VERIFY 점수 표시

**목적.** SOUL 버전과 모델 쌍(예: 같은 SOUL을 Opus → Sonnet으로 옮겼을 때)마다 SOUL VERIFY 점수를 장부 기록에 연결해 보여 준다.

**사용자 흐름.**
1. SOUL VERIFY 실행 결과(보고서 + 점수) 생성 → 보고서 파일의 SHA-256을 `reportHash`로, 점수를 `scoreBps`(0~10000)로 기록.
2. 조회 페이지: 버전 노드(③)나 버전 목록에서 "점수 N건" 배지 → 펼치면 `from모델 → to모델, 점수 %, 보고서 해시, 날짜`.
3. 보고서 원문은 별도 공개 위치(예: soul-verify 저장소)에 두고, 사용자가 파일을 올리면 해시로 일치 확인.

**필요한 변경.**
- 컨트랙트: **없음.** `recordCarryOver(agentId, soulHash, fromModel, toModel, reportHash, scoreBps)`와 `getScores`가 이미 있다(기록된 soulHash만 허용, owner만 호출).
- 스크립트: `scripts/record-score.js`(soul-verify 결과 JSON → `recordCarryOver` 호출; **이 호출은 트랜잭션이므로 사용자 승인 후**), `scripts/export-scores.js`(`getScores` 읽기).
- 화면: 버전별 점수 배지·표. 점수 의미(어떤 실험·몇 회·어떤 채점 방식)는 보고서 해시로 연결하고 화면에 점수 단독으로 "신뢰 점수"처럼 보이지 않게 한다.
- 무료 경로: 지금 점수 기록은 owner 직접 트랜잭션뿐이다. 지갑 없는 사용자를 위해서는 점수 항목용 EIP-712 타입을 추가하는 컨트랙트 변경이 필요할 수 있다. MVP는 직접 기록 + 읽기 화면만, 서명형은 후속.

**위험.**
- 점수의 자기 보고: 소유자가 유리한 결과만 기록할 수 있다. 화면에 "소유자 기록"이라고 표기하고 보고서 해시·실험 조건(n, 모델 버전)을 필수 필드로 둔다.
- 점수 과대 해석: 한 번의 점수가 "정체성이 이어졌다"는 증명은 아니다(soul-verify 논문의 한계와 동일). 문구에 단정 금지.
- `fromModel`/`toModel` 표기가 자유 문자열이라 같은 모델이 여러 철자로 흩어질 수 있음 → 표기 규약(`provider/model@date`) 문서화.
- 실험 채점 관련: 점수에 쓰는 판정은 판정자에게 시험 내용을 알리지 않는 방식(익명 라벨)을 따랐는지 보고서에 기재.

**작업량.** 소~중 (읽기 화면 + 기록 스크립트).

## ⑤ 암호화 백업과 복원

> 상태: **설계 초안, 구현 전.** 이 절은 문서만 추가했고 코드·배포·업로드는 하지 않았다.

**목적.** SOUL·MEMORY·일지처럼 AI를 이루는 요소를 PC가 없어져도 지키고, 어느 컴퓨터에서든 다시 깨울 수 있게 한다.

### 1. 원칙

- **내용은 체인에 올리지 않는다.** 체인은 공개되고 영구히 남아, 올리면 되돌릴 수 없다.
- 클라이언트(내 PC)에서 **먼저 암호화한 묶음**(SOUL, MEMORY, 일지 등)만 분산 저장소에 올린다.
- 장부에는 **묶음 지문(SHA-256)과 저장 위치(CID 또는 Arweave tx id)** 만 남긴다. 암호화한 파일이어도 길이·시점은 보이므로, 지문은 암호문 기준으로 계산한다.
- 암호화 전 평문의 지문은 기존 `soulHash`와 같은 방식으로 따로 두어, 복원 후 대조에 쓴다.

### 3. 암호화와 키

- **표준 도구만 쓴다.** `age`(파일 암호화, 비밀번호·키 파일 방식) 또는 libsodium의 대칭 암호(`secretbox`). 직접 만든 암호는 쓰지 않는다.
- **키는 소유자(사람)만 가진다.** 서비스·에이전트·운영자는 키를 갖지 않는다.
- **키를 잃으면 복구할 수 없다.** 복구 창구를 만들지 않는다(만들면 그게 약점이 된다).
- 키 백업(안):
  1. **종이에 적어 서로 다른 두 장소**(집 보관함 + 신뢰하는 다른 장소)에 둔다.
  2. 디지털 사본은 암호화된 USB 등 **오프라인**으로만. 클라우드 동기화 폴더에 두지 않는다.
  3. 복원 연습: 연 1회, 종이 키로 실제로 복호화되는지 확인한다.
- **키는 절대 체인·저장소(git)·로그·채팅에 넣지 않는다.** 암호문 파일도 키와 같은 곳에 두지 않는다.

### 4. 복원 흐름

1. **새 컴퓨터** 준비(OpenClaw 같은 하네스 설치).
2. 장부에서 에이전트의 최신 **묶음 지문·저장 위치**를 읽고 묶음을 **내려받는다**.
3. 암호문 지문을 장부 기록과 **대조**한다(`scripts/check-soul.js` 재사용; 다르면 중단).
4. 소유자 키로 **복호화**한다(키는 종이에서 직접 입력).
5. 복호화한 평문의 `soulHash`를 장부와 한 번 더 대조한다.
6. 하네스에 SOUL·MEMORY를 넣어 **깨운다.**

**테세우스의 배 메모와 연결.** 복원은 한 번에 통째로 바꾸지 않고 **하나씩 옮긴다**: SOUL 먼저 → 약속·말투 확인 → 기억 일부 → 나머지. 각 단계마다 지문 대조와 SOUL VERIFY를 하고, 어긋나면 그 단계에서 멈춘다.

### 5. 한계 (정직하게)

- **모델 자체(Claude 등)는 옮길 수 없다.** 백업되는 것은 SOUL·MEMORY 같은 **설명과 기록**이다. 모델은 공급자 것이며 사라지거나 바뀔 수 있다.
- **깨어난 AI가 같은지는 이 설계가 증명하지 못한다.** SOUL VERIFY로 **따로 재야** 하며, 점수도 "같다"는 증명은 아니다(④의 위험 절과 동일).
- **블록체인 안에서 AI를 '운용'하는 것은 계산 비용 때문에 현실적이지 않다.** 체인은 지문·위치 같은 작은 기록용이다.
- 위 (b) '블록체인이 꼭 필요한가' 표(결 리뷰)와 같은 결론이다: **지문·시각·점수 연결은 OpenTimestamps(OTS)로 충분한 부분이 많다.** ⑤에서 체인이 더하는 것은 "저장 위치·지문의 공개 조회 위치"뿐이며, 이것도 공개 저장소 + OTS로 대체 가능하다. 따라서 ⑤의 필수 요소는 체인이 아니라 **암호화·키 관리·복원 연습**이다.
- 저장소 소멸, 키 분실, 암호화 도구 취약점 위험이 남는다. 오래 지나면 암호 알고리즘이 약해질 수 있어 **주기적 재암호화(새 키로 재업로드)** 가 필요할 수 있다.

### 6. SOUL VERIFY v1.1·v1.4a 결과와 복원 옵션

오늘(2026-10-28) v1.1 결과: **몸(모델)을 바꿔도 말투와 약속은 유지됐지만, 기억은 −0.21 떨어졌다.** 그래서 복원 시 기억 처리를 **선택**하게 한다.

| 옵션 | 내용 | 장점 | 위험 |
|---|---|---|---|
| A. 기억 통째로 | MEMORY 전체를 그대로 넣는다 | 정보 손실 최소 | 길고 낡은 기억이 섞이거나 새 모델이 일부를 놓칠 수 있음 |
| B. 핵심 고정 | 핵심 사실·약속만 추려 SOUL에 고정, 나머지는 필요할 때 검색 | 짧고 안정적일 수 있음 | 무엇이 핵심인지 고르는 과정에서 정보 손실·편향 |

**v1.4a 결과(2026-10-28, 사전등록 후 검증).** 검색만 쓰는 몸에서 '핵심 고정'(교정·결정·선호 최신 20개를 항상 포함)을 더했다. 기억 정확도는 검색만 0.790, 핵심 고정 0.854, 전체 기억 0.998이다(핵심 고정 − 검색만 = +0.064, 95% CI [0.007, 0.128], 경계선에서 지지; 약속 점수는 약해지지 않음 −0.016).
- **고정한 기억은 완전히 회복됐다.** 고정 대상 문항은 0.808 → 1.000이고, 검색이 그 항목을 못 찾아도 회복됐다.
- **고정하지 않은 기억은 회복되지 않았다.** 고정 밖 문항은 0.777 → 0.750(회복 없음)이고, 검색이 빗나가는 먼 문항 중 고정 밖은 0.429 그대로다. 전체 손실(−0.208) 중 약 3분의 1(0.31)만 메웠다.
- **전체 기억(옵션 A)이 상한이다.** 0.998로 사실상 손실이 없다. 핵심 고정은 이 상한에 못 미친다.
- 한계: 합성 에이전트 2개·모델 1개·고정 규칙 1개이며, 사람이 채점을 확인하지 않았다(키 + LLM 판정 2종).

**권장: '핵심 고정 + 가능하면 전체 기억'.** 전체 기억이 상한이므로 길이·비용이 허락하면 A를 쓰고, 그럴 수 없을 때는 핵심 고정(B)을 **최소 보장**으로 함께 둔다. B만 쓰면 고정 규칙 밖의 기억은 잃는다. 복원 도구는 두 옵션을 모두 제공하고, 선택·점수는 ④처럼 보고서 해시로 연결해 기록한다.

근거: soul-verify 커밋 [`3d08d49`](https://github.com/YA-TONGSIN/soul-verify/commit/3d08d49) (v1.4a 결과). 사전등록은 `5fc0fa4`.

## 후속 설계 메모 (결의 리뷰, 2026-10-28)

두 가지 모두 **설계 메모일 뿐 구현 전**이며 컨트랙트는 바꾸지 않았다.

### (a) '확인된 갈라짐' — 부모 소유자의 EIP-712 서명

**문제.** 현재 `fork-of:<agentId>@v<n>` 표기는 새 에이전트 소유자의 자기 신고라 누구나 남의 해시를 부모라 적을 수 있다. 부모 에이전트의 소유자가 "이 fork를 인정한다"고 서명하면 '부모 확인'으로 올릴 수 있다.

**서명 내용(안).** EIP-712 타입 `ForkEndorsement(uint256 parentAgentId, bytes32 parentSoulHash, uint256 childAgentId, bytes32 childFirstSoulHash)`. 도메인은 기존 `SoulRegistry` 도메인(체인·컨트랙트 주소 포함)을 재사용해 다른 체인·컨트랙트로의 재사용을 막는다. 서명자는 서명 시점의 부모 에이전트 소유자여야 한다.

| 비교 | 오프체인 서명 | 컨트랙트 함수 (`endorseFork`) |
|---|---|---|
| 컨트랙트 변경 | 없음 | 있음(재배포·재검증 필요) |
| 비용 | 0원. 서명 파일을 공개 저장소·화면 입력으로 전달 | 건당 트랜잭션 가스(부모 소유자가 직접 호출) |
| 검증 | 누구나 서명 복구 + `getAgent(parent).owner` 대조. 단, 소유자가 이후 바뀌면 '서명 당시 소유자'를 알 수 없음 | 체인이 소유자 확인, 기록 시각·순서가 체인에 남음 |
| 철회 | 어려움(이미 퍼진 서명) → 만료·nonce 필요 | `revokeEndorsement` 같은 함수로 가능하나 기록은 남음 |
| 한계 | 서명이 어디 있는지 찾기 어렵고 누락될 수 있음 | 지갑 없는 부모 소유자 불가, 가스 필요 |

**권고.** MVP는 오프체인 서명(컨트랙트 변경 없음) + 서명 묶음을 `batches/`와 같은 방식으로 공개 파일에 두고 화면이 읽어 검증. 서명 당시 소유자 문제가 실제로 생기거나 선후 증명이 필요해지면 그때 컨트랙트 함수를 검토한다.

**화면 구분(안).**
- **자기 신고**: 회색 배지 「자기 신고 · 검증되지 않음」 + **점선** 선(기존 표기 유지).
- **부모 확인**: 초록 배지 「부모 확인됨」 + **실선** 선, 배지 호버·펼침에 서명자 주소·서명 해시·서명 날짜 표시.
- 서명이 있어도 부모 해시가 장부에 없으면 확인 표시를 하지 않고 별도 줄로만 노출. 색에만 의존하지 않도록 배지 문구와 선 모양을 함께 쓴다(접근성).
- 문구 주의: '부모 확인됨'은 "부모 소유자가 이 fork를 인정했다"는 뜻일 뿐, 내용이 실제로 파생됐다는 증명이 아니다.

### (b) '블록체인이 꼭 필요한가'

기준: **운영자를 믿지 않는 외부인**이 직접 확인해야 하는 것인가.

| 항목 | 체인이 필요한가 | 대안 / 설명 |
|---|---|---|
| 추가만 가능한 순서(앞 기록을 몰래 고치거나 끼워 넣을 수 없음) | **필요에 가까움** | 해시 체인 + 공개 로그(투명성 로그)로도 가능하나 로그 운영자를 믿거나 감시자가 필요. 여러 주체가 쓰는 공통 순서는 체인이 가장 단순 |
| 기록 시각(그 시점에 이미 있었다) | 대부분 **불필요** | OpenTimestamps(비트코인 앵커)로 충분. 체인 블록 시각은 같은 역할을 더 비싸게 함 |
| 소유자 서명(누가 올렸나) | **일부 필요** | 서명 자체는 오프체인 EIP-712로 충분. '현재 소유자가 누구인지'와 이전(`transferAgent`)의 합의는 체인이 편함 |
| 파일 지문 일치 확인 | 불필요 | 로컬 해시 계산 |
| 변조 알림(`check-soul`) | 불필요(읽기용으로만 체인 사용) | 로컬 기준 파일 + OTS면 충분 |
| 점수·보고서 연결(`reportHash`) | 불필요 | 공개 저장소·Zenodo DOI + OTS로 충분. 체인은 소유자 자기 기록일 뿐 |
| 계보(fork) 표기 | 불필요 | 오프체인 부모 서명(위 (a))으로 충분 |
| 무료 묶음 등록 | 체인은 하루 1회 앵커용 | 앵커 대신 OTS 묶음도 가능 |

**정직한 결론.** 지금 장부가 하는 일의 상당 부분은 **로컬 파일 + OpenTimestamps만으로 된다**(지문 일치, 기록 시각, 점수·보고서 연결, 계보 서명). 체인이 실제로 더해 주는 것은 좁다: ① 여러 소유자가 함께 쓰는 **공통의 추가 전용 순서**, ② 소유자(주소)의 **이전·현재 소유 상태** 같은 공유 상태, ③ 운영자가 사라져도 남는 공개 조회 위치. 이 세 가지가 실제로 쓰이기 전까지 체인은 "있으면 편한 것"이지 "없으면 안 되는 것"이 아니다. 따라서 메인넷 배포 결정 전에 (1) OTS만 쓰는 최소 버전과 (2) 현재 방식을 비교하고, 외부 사용자가 ①~③을 실제로 필요로 하는지 먼저 확인한다.
