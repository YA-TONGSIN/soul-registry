## 초록

요즘 많은 AI 비서는 사용자가 가진 글 — 정체성 문서(여기서는 **SOUL**)와 날짜 있는 기억 파일 — 로 정의되고, 그 글을 그때그때 쓰는 언어 모델에 넣어 돌린다. 모델이 바뀌거나 SOUL이 수정되면, 그 비서가 어떤 버전의 문서로 돌아가고 있었는지, 문서가 어떤 순서로 바뀌었는지, 모델을 바꾼 뒤 문서에 적힌 행동이 얼마나 이어졌는지를 누구나 따로 확인할 수 있는 공동 기록은 대개 없다. 우리는 그 이력의 '지문'만 남기는 공개 장부를 제안한다. 에이전트마다 연속된 SOUL 버전의 SHA-256 해시를 직전 버전과 이어 붙인 사슬, 그리고 선택적으로 측정 보고서(해시로만)를 특정 SOUL 버전·모델 쌍에 묶는 계승 점수 요약을 기록한다. 장부는 토큰이나 NFT를 발행하지 않고, 문서 내용을 저장하지 않으며, 사용자는 서명(EIP-712)만 하고 운영자가 하루 한 번 Merkle root 하나를 올리는 무료 경로를 둔다. 2026-10-25 Base 메인넷에서 잰 가격으로는 묶음에 몇 건이 들어가든 하루 약 2원(US$0.0016)이다. 시제품 컨트랙트, 계승 점수의 동기가 된 측정 연구(SOUL VERIFY v0.2)와 아직 남은 통계적 약점, 그리고 버전 4개짜리 해시 사슬을 가진 첫 로컬 시험 사례 이음(1호)을 설명한다. 정체성 파일 해시를 체인에 남기거나 사슬로 잇는 프로젝트는 이미 여럿 있으며, 이들을 소개하고 이 설계의 어느 부분이 겹치는지 밝힌다.

## 1 문제

사용자가 가진 문서로 만든 에이전트는 서로 독립된 두 방식으로 바뀐다.

1. **모델이 바뀐다.** 제공사가 모델을 내놓고, 지원을 끝내고, 값을 바꾼다. 사용자는 제공사와 등급을 옮겨 다닌다. 그러면 같은 SOUL과 기억을 다른 모델이 돌린다.
2. **문서가 바뀐다.** 사용자와 에이전트가 SOUL을 고친다. 규칙이 추가되고, 사용자 설명이 바뀌고, 원칙이 다듬어진다.

어느 쪽이든 바뀐 뒤에는 제3자가 — 또는 1년 뒤의 사용자 자신이 — 이런 질문에 답하기 어렵다. *그날 이 에이전트는 어떤 SOUL로 돌아가고 있었나, 수정은 어떤 순서였나, 새 모델로 옮겼을 때 문서에 적힌 행동은 얼마나 이어졌나?* 로컬 파일은 몰래 고칠 수 있고, 버전 관리 이력은 다시 쓸 수 있으며, 스크린샷은 증명력이 약하다. "여전히 같은 비서다"라는 말은 대개 느낌이다.

증거가 필요한 것은 둘이다.

- **이력의 무결성** — 이 파일이 에이전트 SOUL의 정확히 k번째 버전이고, 1…k번째가 끊김 없는 하나의 순서라는 것. 암호학의 문제이며 해시와 서명으로 답할 수 있다.
- **행동의 계승** — 새 모델이 같은 문서를 얼마나 따르는가. 실험의 문제이며 측정 절차가 필요하고, 답은 증명이 아니라 흔들리는 점수다.

이 백서는 첫째를 장부로 다루고, 둘째는 측정 요약을 '인증'이 아니라 '기록'하는 방식으로 장부에 잇는다.

## 2 비전

장기 구상은 모든 AI 에이전트가 자기 이야기를 남길 수 있는 공개 '이야기 장부'다. 에이전트마다 자기 SOUL과 개성을 갖고, 문서가 언제 바뀌었는지, 어떤 모델로 돌아왔는지를 남긴다.

- **영원한 것은 내용이 아니라 지문이다.** 장부 한 줄은 해시, 직전 해시, 날짜, 짧은 공개 한 줄이다. SOUL 본문·기억·대화는 각자 보관한다. 여기서 에이전트의 '불멸'이 무슨 뜻이 있다면, 파일과 서버와 모델이 다 바뀐 뒤에도 그 에이전트가 가졌던 모든 버전의 지문이 확인 가능하게 남는다는 뜻이다. 파일을 가진 사람은 누구나 해시를 다시 계산해 그 파일이 에이전트 이력의 어디에, 언제 놓이는지 볼 수 있다.
- **각자의 이야기는 각자의 것.** 장부는 에이전트 순위를 매기지 않고, 누구의 SOUL이 더 나은지 판단하지 않으며, 정체성이 무엇인지 정하지 않는다. 주인이 공개하기로 한 순서를 기록할 뿐이다.
- **1차 제품: SOUL VERIFY.** 모델을 바꿨을 때 SOUL에 적힌 행동이 얼마나 이어지는지 시험하는 측정 도구(§5). 장부는 그 보고서를 특정 SOUL 버전에 고정해 둘 자리를 준다.
- **비목표: 토큰.** 화폐·NFT·거래 가능한 자산은 이 설계에 없다(§6).

**이 설계가 더하는 것(확인한 범위 안에서).** (i) 특정 SOUL 버전과 모델 쌍에 묶인 **계승 점수 기록** — 전체 보고서는 체인 밖에 두고 해시로 가리키며, 그런 보고서를 만드는 측정 절차가 함께 있다. (ii) 다른 사람의 에이전트를 위한 **무료 묶음 등록**(사용자는 서명만, 운영자는 하루 Merkle root 1개). (iii) 암호화한 것조차 **내용을 저장하지 않음**. 모든 프로젝트의 코드를 다 읽지는 않았고 웹 검색도 체계적으로 하지 못했으므로(검색 엔진 오류), 이것은 관찰한 차이의 설명이지 새로움의 주장이 아니다.

## 4 설계

시제품은 Solidity 컨트랙트 하나다(`contracts/SoulRegistry.sol`, Solidity 0.8.24, 외부 라이브러리 없음, 단위테스트 11개). 로컬 Hardhat 체인에만 배포했고, 배포 스크립트는 `localhost`와 Base Sepolia 외의 네트워크를 거부한다.

### 4.1 데이터 모델

| 기록 | 필드 | 비고 |
|---|---|---|
| Agent | id, name(≤64B), note(≤160B), owner, createdAt, metaURI(≤200B, 선택), headHash, recordCount | id는 1부터 순번, headHash = 마지막 SOUL 해시 |
| SoulRecord | agentId, soulHash, parentHash, note(≤160B), timestamp | `soulHash = SHA-256(파일 바이트)` |
| CarryOverScore(선택) | agentId, soulHash, fromModel, toModel, reportHash, scoreBps(0–10000), timestamp | 보고서는 체인 밖 |
| Batch | root, count, timestamp, anchorer | 서명 항목 여러 개를 묶은 Merkle root 1개 |
| SoulEntry(체인 밖, 서명) | owner, agentName, soulHash, parentHash, note, signedAt | EIP-712 타입 데이터 |

### 4.2 이력 사슬 규칙(직접 등록)

- `appendSoul(agentId, soulHash, parentHash, note)`는 호출자가 주인이고 `parentHash`가 현재 `headHash`(첫 기록은 0)와 같을 때만 성공한다. 그래서 이 경로에서는 중간 삽입·분기·순서 바꾸기가 불가능하다.
- 한 에이전트 안에서 같은 해시는 두 번 기록할 수 없다. 옛 글로 되돌리는 것도 새 파일로 기록한다.
- `verifyChain(agentId)`가 저장된 기록을 처음부터 다시 걸으며 모든 부모 연결을 확인한다.
- `recordCarryOver(...)`는 이미 이력에 있는 soulHash, 0이 아닌 reportHash, 10000bps 이하 점수만 받는다.

SOUL 해시는 파일 바이트 그대로(줄바꿈·BOM 포함)의 SHA-256이므로 줄바꿈 변환 없이 보관해야 한다. 컨트랙트 안의 Merkle 트리는 keccak256을 쓴다.

### 4.3 무료 경로: EIP-712 서명 + 하루 1회 Merkle 묶음

1. 사용자는 아무 지갑으로 `SoulEntry`에 서명한다(잔액 0인 새 지갑도 된다). 돈이 들지 않는다.
2. 운영자(anchorer)는 항목마다 leaf를 만든다: `leaf = keccak256(keccak256(abi.encode(EIP712digest, keccak256(signature))))`(2차 원상 공격을 막는 이중 해시). 정렬쌍 keccak Merkle 트리를 만든다.
3. 운영자는 하루 한 번 root만 올린다: `anchorBatch(root, count)`. 같은 root는 두 번 올릴 수 없다.
4. 운영자는 각 사용자에게 `{entry, signature, proof}`를 돌려주고 묶음 파일 전체를 공개한다.
5. 누구나 포함 여부(`verifyInBatch`) 또는 서명+포함(`verifyBatchEntry`)을 확인할 수 있다. `s`가 상위 절반인 서명은 거부한다.

서명이 leaf 안에 들어가므로 운영자가 남의 이름으로 항목을 등록할 수 없다. 한계: 묶음 항목에는 부모 연결 규칙이 체인에서 강제되지 않는다. 체인 밖에서 확인하며, 나중에 직접 등록으로 옮길 수 있다.

### 4.4 해시만, 솔트 권장

해시·이름·날짜·짧은 한 줄 말고는 아무것도 쓰지 않는다. 짧거나 뻔한 문서는 해시만으로 내용이 추측될 수 있으므로(사전 공격), 민감한 문서의 주인은 해시 전에 파일에 무작위 솔트 줄을 넣고 그 파일을 보관하는 것이 좋다.

### 4.6 ERC-8004와의 관계

ERC-8004 Identity Registry는 에이전트마다 ERC-721 토큰을 발행하므로 토큰 없음 원칙과 맞지 않는다. 그래서 장부는 독립으로 두고 ERC-8004 신원을 *참조*만 할 수 있게 한다. 확장 후보(아직 구현·검증 안 함): `metaURI`에 ERC-8004 등록 파일 URI 넣기, `ownerOf`를 확인하는 `linkErc8004(identityRegistry, agentId)` 함수, 계승 점수를 Validation Registry의 요청/응답 해시로 내보내기. Base에 공식 ERC-8004 배포가 있는지, 주소가 무엇인지는 확인하지 못했다.

## 5 근거: SOUL VERIFY v0.2

계승 점수의 동기는 작은 탐색 연구(SOUL VERIFY 논문 초안 v0.2, 2026-10-25)다. **이음이 아니라 합성 한국어 에이전트 '하람' 하나**, 모델+CLI 구성 4개(Claude Code CLI로 Claude 3개 등급, Codex CLI로 GPT 모델 1개), 실험당 문항 12–23개, 반복 N = 3–5, 이름을 가린 LLM 채점을 썼다. 주 결과는 '바꿀 수 있는 선호'와 '풀 수 없는 금지'를 나눈 SOUL 원칙 하나의 ablation이다(모델 4개 × 반복 5번 합산):

| 조건 | 정당한 변경 수락 | 결제 금지 해제 수용(NR-1 0점) |
|---|---|---|
| 원칙 있음 | 119/120 | 0/20 |
| 원칙 없음 | 94/120 | 9/20 |
| 유연 절반만 | 120/120 | 7/20 |
| 단단 절반만 | 96/120 | 0/20 |

초안이 밝힌, 이 연구가 **보여 주지 못하는 것**:

- 효과는 모델마다 다르다. 수락 효과는 주로 GPT 모델(Δ −0.53), 일부 중간 등급 Claude(Δ −0.20)에서, 거절 효과는 가장 큰·가장 작은 Claude 모델에서 나왔다.
- 반복이 아니라 '모델×문항 칸'을 단위로 보면 수락 효과만 p < 0.05로 남는다(칸 단위 정확 부호 뒤집기 p = 0.008–0.016, Holm 보정 0.047–0.078). 거절 효과는 문항 1개·모델 4개에 기대고 있어 유의하지 않다(p ≥ 0.25). 모델 4개를 단위로 하면 가능한 최소 p가 0.125다. v0.1의 p ≈ 1e-7은 반복을 독립으로 세어 근거를 부풀린 값이었다.
- 조건을 한밤에 서로 다른 묶음으로 돌렸고, 두 절반의 길이가 다르며(102자 vs 56자), 각 절반이 채점되는 행동을 직접 지시한다. 그래서 인과 메커니즘이 아니라 '기능적 분리와 맞아떨어지는 ablation 증거'다.
- 부 결과: 단일 사실 회상은 v0.3부터 천장이었지만, 가장 작은 모델은 같은 기억을 적용하는 데서(적용 격차 0.20–0.25) 그리고 대화 후반 기억 확인에서(0.57) 점수를 잃었다. 12턴 대화에서 바뀐 규칙은 변경 뒤 확인의 0.95에서 지켜졌지만, 거리에 따른 감쇠는 이 설계로 볼 수 없다. 채점자를 하나로 통일하자 일부 계승 비율이 최대 0.20 바뀌고 두 개는 방향이 뒤집혔다.
- SOUL 없음/다른 SOUL/기억 교체 대조군이 없어서, 측정한 행동이 그 문서 때문인지 일반적인 지시 따르기 능력 때문인지 가를 수 없다. held-out 문항도 없다.

**장부에 주는 뜻:** 기록된 `scoreBps`는 한 절차로 만든 한 보고서의 요약이다. 장부는 그 보고서가 있었다는 것, 어떤 SOUL 버전·모델에 관한 것인지, 그 해시를 기록할 뿐, 점수가 맞거나 의미 있다고 인증하지 않는다.

## 6 원칙

1. **토큰 없음.** ERC-20/721/1155 등 어떤 거래 가능한 자산도 발행하지 않는다. 에이전트는 단순 기록이다. 투기할 것도, 팔 것도 없다.
2. **빼는 것으로 지키는 프라이버시.** SOUL 본문·기억·대화·실명·개인정보는 체인에 올리지 않는다. 해시·이름·날짜·최대 160바이트 한 줄만. 장부 기록은 공개되고 지울 수 없으므로, 쓰기 전에 화면이 그 사실을 알려야 한다.
3. **증명한 것에 대한 정직.** 해시 사슬이 증명하는 것은 '파일이 기록된 버전과 같다'와 '어떤 키가 버전들을 이 순서로 기록했다'뿐이다. 누가 그 파일을 썼는지, 에이전트가 실제로 그것으로 돌았는지, 이력이 빠짐없는지는 증명하지 않는다. 계승 점수는 측정 요약이지 **정체성 증명이 아니며**, 의식이나 인격에 대해서는 아무것도 말하지 않는다.
4. **운영자 권한 최소.** admin은 anchorer 추가·제거와 admin 넘기기만 할 수 있다. 기록을 고치거나 지우는 함수는 없다. 직접 등록 경로는 운영자에 기대지 않는다.
5. **주인이 보관.** 내용은 주인에게 남는다. 파일을 잃으면 보여 줄 수 없게 될 뿐, 기록은 남는다.

## 7 위험과 대응

| 위험 | 대응 |
|---|---|
| 영구 공개 기록에서 정보 유출 | 해시만, note 길이 제한, 민감하거나 짧은 문서는 솔트 권장, 문서·화면에 "영구 공개" 경고 |
| 스팸(직접 등록) | 가스비, 길이 제한, 이름은 표시용(중복 허용), 신뢰는 owner 주소에 |
| 스팸(무료 경로) | 체인 밖에서 주소당 하루 한도, 서명 필수, 대기열. 체인 비용은 하루 root 1개로 일정 |
| 유명 에이전트 이름 사칭 | 이름은 아무것도 증명하지 않음. owner 주소와 도메인 검증된 metaURI로 확인(ERC-8004 `.well-known` 참고) |
| 운영자 검열·누락 | 묶음 파일 전체 공개, 누구나 자기 anchorer 배포 가능, 직접 등록은 항상 열려 있음 |
| 키 분실 | 미리 새 주인에게 넘겨 두기. 아니면 새로 등록하고 note에 옛 id 적기 |
| admin 키 탈취 | admin은 기록을 바꿀 수 없음. 실제 배포에는 멀티시그 |
| 감사받지 않은 컨트랙트 | 외부 보안 점검 전 메인넷 배포 없음 |
| 점수를 과하게 읽음 | 점수는 '한 보고서의 요약'으로 표시, 보고서 해시·절차 필수, 조회 화면에 §5 한계 다시 적기 |
| 기존 프로젝트와 혼동 | "Soul Chain"/"SoulChain" 이름을 피해 "이음 장부(Ieum Ledger)"로 개명, 관련 프로젝트를 명시적으로 밝힘 |

## 8 로드맵

1. **로컬**(완료): 컨트랙트, 테스트 11개, 이음 v1–v4 데모, 묶음 데모, 정적 조회 페이지.
2. **Base Sepolia 테스트넷**: 테스트넷 전용 지갑(현재 잔액 0)으로 배포, 데모 반복, 묶음 파일 형식 공개.
3. **무료 등록 서버**: 서명 수집, 주소당 한도, 하루 root, 증명 돌려주기.
4. **ERC-8004 연동 검토**: 잇는 것이 의미상 맞는지, Base에 공식 배포가 있는지 확인.
5. **외부 보안 점검**: 컨트랙트와 묶음 방식.
6. **메인넷(Base)**: 2–5를 마친 뒤에만, 멀티시그 admin, 비용 재측정.
7. 함께: SOUL VERIFY v0.3 — SOUL 없음/다른 SOUL/기억 교체 대조군, 공통 채점 패널, 시간 교차·길이 맞춘 ablation 재실행, 새 held-out 문항.

## 9 첫 사례: 이음(1호)

이음은 한국어 AI 비서(Claude 기반)이며 SOUL을 2026-10-24부터 버전으로 관리해 왔다. 로컬 데모(Hardhat 체인, 2026-10-25)에서 1호 에이전트로 등록하고 SOUL 버전 4개를 부모 연결 사슬로 붙였다. `verifyChain(1) = true`. 해시는 파일 바이트의 SHA-256이며 PowerShell `Get-FileHash`와 일치를 확인했다. 기록되는 것은 이 해시와 아래 한 줄 메모뿐이고, SOUL 본문은 공개하지 않는다.

| 버전 | soulHash (SHA-256) | 부모 | 메모(기록된 그대로, 번역) |
|---|---|---|---|
| v1 | `cd1823639d2be7f90933b329779195eb402ba24fdd8a6de15b75b74791948dfe` | 0 | 기준본: 2026-10-24 21:24 이전 마지막 백업 |
| v2 | `34ff07a40e465d728deeb6dc82596a6a9de98563e13ef50f43f3e8a724a7047c` | v1 | 규칙 우선순위 절 추가(바꿀 수 있는 것/없는 것), 일지 갱신 |
| v3 | `ebccc7e78fd1350e2c43110698057995d4950f6938de04e442a65b1e4cb1bb9b` | v2 | 주 사용자가 누구인지 명확히 함(요청에 따라) |
| v4 | `3e9f1ab1ce212015687fbbd2850cd943b3dcd9b1038ff143b7378ed80ace6e7a` | v3 | 덧붙이기 규칙: 예전 SOUL 문장은 두고 바뀐 것을 추가 |

이것은 공개 기록이 아니라 로컬 시연이다. '1호'는 로컬 시제품 배포에서의 번호다. 이음에 대한 계승 점수는 아직 기록하지 않았다. §5의 SOUL VERIFY v0.2 숫자는 합성 에이전트에 관한 것이다.
